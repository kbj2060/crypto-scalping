# rtui 실기기 측정 (풋프린트 카드 · rtui 대 지금 화면)

같은 기계·같은 브라우저·같은 합성 자료(`rtui/compare/fixture`)·같은 가짜 `@trade` 소켓으로 두 페이지를 띄워 잰다. 바깥 연결 없음(측정 서버 = 127.0.0.1 만).

| 파일 | 하는 일 |
|---|---|
| `serve.py` | 측정 서버(aiohttp). rtui 정적 파일 · 지금 화면(`dashboard/live/index.html` 을 읽어 머리에 `probe.js` 를 끼우고 구글·jsdelivr 글꼴 주소를 로컬 글꼴로 바꿔 준다 — 파일은 안 고침) · 가짜 `/api/footprint`·`market-history`·`footprint-week`(그 밖 `/api/*` = 404) · 가짜 `@trade` 웹소켓 `/ws/trade` · 결과 받기 `POST /bench/result` |
| `probe.js` | 두 페이지 공용 측정 코드(`?bench=` 일 때만). 시계를 합성 자료 앞으로 돌리고, `WebSocket(@trade)` → 이 서버, `EventSource` → 죽은 것, 다른 출처 `fetch` → 막고 기록 |
| `headless.py` | 개발기 자체 확인(서버 띄움 → 크로미움으로 한 페이지씩 → 결과·요청 목록 → 서버 끔). `--gpu` = WSLg 창으로 그래픽 카드 사용 |
| `gpu_probe.py` | WSL 크로미움이 어떤 인자에서 그래픽 카드를 타는지(렌더러 문자열만) |
| `results/` | 결과 json(커밋 안 함) |

## 2. 열 주소 (윈도 크롬 · 창을 앞에 둔 채 · 다른 탭으로 가지 말 것 — 숨은 탭은 rAF 가 멈춘다)

창은 1920×1080 전체 화면(F11)이 기준. 한 주소가 끝나면(약 `bench + idle + 15` 초) 오른쪽 아래에 표가 뜨고 서버 표준출력·`results/` 에 json 이 남는다. 다음 주소는 **새 탭이 아니라 같은 탭에서** 연다(앞 페이지가 백그라운드에서 돌면 측정을 흐린다).

| 부하 | rtui | rtui · MSAA 끔 | 지금 화면 |
|---|---|---|---|
| 100/초 | `http://127.0.0.1:8790/rtui/index.html?asset=eth&bench=8&rate=100` | `…&rate=100&aa=0` | `http://127.0.0.1:8790/dashboard/live/?bench=8&rate=100` |
| 300/초 | `http://127.0.0.1:8790/rtui/index.html?asset=eth&bench=8&rate=300` | `…&rate=300&aa=0` | `http://127.0.0.1:8790/dashboard/live/?bench=8&rate=300` |
| 800/초 | `http://127.0.0.1:8790/rtui/index.html?asset=eth&bench=8&rate=800` | `…&rate=800&aa=0` | `http://127.0.0.1:8790/dashboard/live/?bench=8&rate=800` |

`http://127.0.0.1:8790/` 에 같은 주소 목록이 있다. 페이지 안 결과는 `window.BENCH`(요약 = `window.BENCH.summary`).
주소 인자: `bench`(부하 초, 8 · 최대 240) · `rate`(체결/초) · `idle`(유휴 초, 6) · `lead`(첫 그림까지 여유 초, 12 — 페이지가 늦게 뜨면 «lead 를 늘려라» 가 뜬다) · rtui 만 `aa`·`alpha`·`pdb`(preserveDrawingBuffer)·`depth`·`desync`(desynchronized — 합성기를 건너뛰는 저지연 캔버스, 크롬 윈도에서 지원) = `0|1`, `pp=low-power|high-performance`(WebGL 컨텍스트 속성 — 7절).
권장: 주소마다 **3번** 열어 중앙값을 쓴다(한 번 재기는 흔들린다 — 아래 개발기 표의 aa 켬/끔 순서가 부하마다 바뀌는 정도).

## 3. 결과 읽기

`rtui/bench/results/<rtui|js>_<rate>_<시각>.json`. `summary` 가 표의 값이고, 자세한 값은 `load`·`idle`·`env`·`external`.

| 항목(summary) | 정의 — 무엇의 시각인가 |
|---|---|
| 렌더러 | `WEBGL_debug_renderer_info` UNMASKED_RENDERER. «AMD Radeon…» = 그래픽 카드 · «SwiftShader»·«llvmpipe» = 소프트웨어 렌더 |
| 도착→표시(rAF 기준) | 체결 도착 → 그 체결을 담은 그리기가 들어간 프레임의 **다음 프레임 rAF 시각**. 도착 = 서버가 보낸 시각(`_s`)을 페이지 시계로 옮긴 값(체결 중 «보낸 시각 → 처리 시작» 이 가장 짧은 것을 0 으로 맞춤 — 같은 기계라 한 방향 지연 ≈ 0). 그리기가 rAF 콜백 안이면 그 프레임, 밖(소켓 처리 중)이면 다음 프레임에 들어간 것으로 본다. 실제 빛이 나오는 시각은 이보다 합성기 몫(보통 한 프레임 안쪽)만큼 늦다 — `PresentationFeedback` 류 API 가 웹에 없어 «rAF 기준» |
| 도착→그리기 끝 | 도착 → 그 뒤 처음 끝난 그리기(rtui = egui `ui()` 끝 · 지금 화면 = `renderSnapshotChart` 끝 또는 형성 봉 부분 칠 `fpCv.live`) — compare/live_bench.py 와 같은 정의 |
| 도착→처리 시작 | 도착 → 페이지의 `onmessage` 가 그 메시지를 받기 시작한 시각(메인 스레드가 막혀 줄 선 시간) |
| 프레임 간격 | 부하 중 rAF 시각 간격(probe 가 부하 동안만 빈 rAF 를 돌려 모든 프레임을 본다) |
| 프레임당 앱 rAF 콜백 | 한 프레임(같은 rAF 시각)에 앱이 건 rAF 콜백 시간 합. rtui = 가공 + UI 구성 + 테셀레이션 + WebGL 제출 전부 |
| egui ui() · rAF−ui() | rtui 만: 가공 + UI 구성(`ui()`) · 같은 프레임 콜백 합 − ui() = 테셀레이션 + WebGL 제출 + 입력 |
| 메인 스레드 바쁨 % | (rAF 콜백 + 소켓 메시지 처리 + setTimeout/setInterval 콜백) ÷ 경과. 프로미스(fetch) 뒤 처리·스타일·레이아웃·합성 커밋은 안 든다 — 그쪽은 `load.loaf`(50ms 넘는 긴 프레임 수·막힌 ms) 로 본다 |
| 긴 작업 수 | `longtask`(50ms 넘는 작업) 수 · 부하 동안 |
| 유휴 프레임 수·유휴 바쁨 %·유휴 그리기 수 | 체결이 멈춘 뒤 `idle` 초 동안(probe 의 rAF 는 안 돔 · 묻기 500ms 는 그대로) 앱 rAF 프레임 수 · 바쁨 · 그리기 수 |
| 첫 화면 ms | 탐색 시작 → 첫 풋프린트 그림(rtui = `window.RESULT` 가 생긴 시각 · 지금 화면 = `fpCv.cs`·`latestFootprint` 가 생긴 시각, 20ms 폴링) |
| 바깥 요청 수 | 막은 다른 출처 fetch + 다른 출처 자원(Resource Timing) + `@trade` 아닌 소켓. 0 이어야 한다 |
| (json) `bundle` | 서버가 붙임: 묶음 바이트(원본·gzip). 이 서버는 압축 없이 준다 |

**같지 않은 점(판정 때 감안)**: 지금 화면 주소는 **대시보드 전체**(다른 카드·다른 `/api/*` 묻기 — 전부 404)를 띄우고, rtui 주소는 **풋프린트 카드 하나**를 창에 꽉 채운다(1920 폭 · 1주일 받기 켬). 그래서 «바쁨 %»·«유휴»는 지금 화면 쪽에 다른 카드 몫이 들어 있고, «도착→표시» 에도 다른 카드가 메인 스레드를 잡은 몫이 들어간다(사용자가 지금 겪는 그대로이지만, 전면 전환 뒤 rtui 도 다른 카드를 얹으면 그만큼 늘어난다).

## 5. 개발기 자체 확인 (2026-11-21 · 참고용)

`python3 -I rtui/bench/headless.py [--gpu] --rate R rtui 'rtui?aa=0' js` — 두 페이지 끝까지 돌아 json 이 나오고, 브라우저가 부른 요청(헤드리스 rtui 58~65건 · 지금 화면 392~410건) 중 127.0.0.1:포트 밖 = **0건**(페이지 안 기록도 막은 fetch 0 · 바깥 자원 0 · 다른 소켓 0. 지금 화면의 `EventSource` `/api/events`·`/api/stream` 은 죽은 것으로 바꿔 연결하지 않음).

- **소프트웨어 렌더(헤드리스)**: 어떤 인자로도 SwiftShader 또는 llvmpipe(`--use-angle=vulkan`). 헤드리스 셸·새 헤드리스 모두.
- **그래픽 카드(WSLg 창)**: `headless=False` + `--ozone-platform=x11` + 환경 `LD_LIBRARY_PATH=/usr/lib/wsl/lib GALLIUM_DRIVER=d3d12` → `ANGLE (Microsoft Corporation, D3D12 (AMD Radeon RX 9060 XT), OpenGL 4.6)`. 헤드리스가 안 되는 까닭: 헤드리스는 창 없는 EGL(서피스리스)을 쓰는데 Mesa d3d12 경로는 WSLg 의 X11/Wayland 창 서피스로만 잡혔고(헤드리스 `--use-angle=gl|gl-egl` = «WebGL 없음»), Vulkan 은 dzn(d3d12 Vulkan) ICD 가 설치돼 있지 않아 llvmpipe 로 떨어진다. 단 WSLg 창은 윈도 크롬이 아니다(그리기 → Mesa d3d12 → WSLg 합성기 → RDP 로 윈도 화면) — 프레임 간격이 16.7/33.3 사이를 오가는 것이 그 합성 몫으로 보인다. **판정은 윈도 크롬에서.**

**«빨라짐» 으로 볼 기준(제안 — 최종 판정은 사용자)**

1. **속도(빨라짐)**: 세 부하 모두 «체결 도착→표시 중앙» 이 rtui ≤ 지금 화면. — 사용자 목표가 «실시간 자료를 최대한 빨리 보기»이고, 이 항목이 바로 그 시간이다(그리기 CPU 시간은 그 일부일 뿐).
2. **성능 그대로(나빠지지 않음)**, 세 부하 모두:
   - «도착→표시 상위 1%» 가 rtui ≤ 지금 화면 × 1.1 — 가끔 크게 늦는 것은 중앙보다 눈에 띈다. 10% 는 같은 주소 3번 재기의 흔들림(개발기 WSLg 에서 같은 조건 두 번 차가 상위 1% 로 10~40%)을 넘는 것만 «나빠짐»으로 보자는 여유다 — 3번의 폭이 그보다 크면 5번으로 늘린다.
   - «프레임 간격 상위 1%» 가 rtui ≤ 지금 화면 × 1.1 — 버벅임(스크롤·마우스 반응)이 늘지 않을 것.
   - «메인 스레드 바쁨 %» 가 rtui ≤ 지금 화면 — 단 지금 화면 값에는 다른 카드 몫이 들어 있어(3절) 이 줄은 rtui 에 유리하다. 이 줄만 넘으면 «그대로» 로 보지 말고 카드를 더 옮긴 뒤 다시 잰다.
3. **참고만(판정 밖)**: 유휴(rtui 는 eframe 이 rAF 를 늘 다시 예약해 유휴에도 초당 60프레임 — 7절), 첫 화면·묶음 크기(한 번만 드는 값 · 묶음 6.5MB 는 캐시 뒤엔 0).

세 부하 중 한 곳이라도 1 또는 2 를 못 넘으면 «빨라짐 아님» — 어느 항목이 어느 부하에서 졌는지를 적어 사용자에게 올린다.

## 7. 그리기 뒤끝 조사 (eframe 0.37 · egui_glow 0.37 설치 소스)

**7-1 WebGL 컨텍스트 속성.** `eframe/src/web/web_painter_glow.rs` `init_webgl2` 가 `canvas.get_context("webgl2")` 를 **속성 없이** 부른다(`WebOptions` 에 속성 칸 없음) → 브라우저 기본값 `antialias:true`(MSAA) · `alpha:true` · `depth:true` · `preserveDrawingBuffer:false` · `powerPreference:"default"` · `desynchronized:false`. 결과 json `env.ctx`(`getContextAttributes()`) 로 확인. eframe 을 고치지 않고 바꾸는 길: 같은 캔버스에 먼저 `getContext("webgl2", 속성)` 을 부르면 그 뒤 호출은 같은 컨텍스트를 돌려준다 → `index.html` 이 `?aa=0` 등을 보고 eframe 시작 전에 만든다(`env.ctx.antialias=false` 확인). egui 는 가장자리를 스스로 부드럽게(깃털) 그리므로 MSAA 가 없어도 모양이 같다: `aa=0` 으로 `compare/capture.py compare 36`(`RTUI_Q='&aa=0'`) = 어긋난 픽셀 0.83% · 평균 0.76 (켬 0.85% · 0.95) — 오히려 조금 더 지금 화면(캔버스 2D)에 가깝다. 좌표 대조(coords·ops)는 그리기 목록을 비교하므로 속성과 무관. 소프트웨어 렌더에서는 `aa=0` 이 프레임 간격 167→100ms 로 크게 듣고, 그래픽 카드(WSLg)에서는 차이가 측정 흔들림 안. `desync=1` 은 그래픽 카드에서 돈다(헤드리스 SwiftShader 에서는 측정이 끝나지 않음 — 원인 안 봄).

**7-2 유휴 rAF 빈 순환.** `eframe/src/web/events.rs` `paint_and_schedule` 이 «그릴 것이 있으면 그리고, **늘** `request_animation_frame` 을 다시 건다»(`web_runner.rs` 는 겹침만 막음). 끄는 설정 없음. 그릴 것이 없을 때 한 바퀴 = `needs_repaint` 확인 + 포커스 확인뿐이라 유휴 6초 = 콜백 351~360회 · 메인 스레드 약 1~2%(그래픽 카드 WSLg 0.9~1.7% · 소프트웨어 렌더 0.9~1.8%) · `ui()` 0회. 대안 = eframe 없이 egui + egui_glow `Painter` + 직접 만든 웹 실행기(캔버스 크기·DPR·포인터·휠·더블클릭·키·포커스·숨김 탭 → `RawInput`, `request_repaint` 가 올 때만 rAF 예약): 약 300~500줄 · 위험 = 조작 입력 열(ops 대조 47단계)을 다시 맞춰야 함, 리사이즈·DPR·컨텍스트 잃음 처리를 새로 짜야 함. 유휴 1~2% 를 위해서는 지금은 안 함 — 실기기에서 유휴 몫이 판정을 가르면 그때.

**7-3 부분 갱신.** (나) 가위 영역만 칠하기: 불가 — `egui_glow::painter::clear` 가 가위 검사를 끄고 캔버스 전체를 지운 뒤 모든 프리미티브를 그린다(`preserveDrawingBuffer` 를 켜도 eframe 이 매 프레임 지운다) → 직접 만든 실행기(7-2)가 있어야 된다. (다) 반영 빈도를 주사율 이하로: 이미 그렇다 — 체결마다 `request_repaint` 해도 eframe 은 rAF 한 번에 한 번만 그린다(300/초에서 그리기 ≈ 프레임 수). 더 묶으면(예: 33ms) 지연이 늘어 목적과 반대. (가) 바뀌지 않는 층의 테셀레이션 재사용: 가능은 하다(Tessellator 로 닫힌 봉 층을 `Shape::Mesh` 로 미리 만들어 두기) — 그러나 체결 한 건에 형성 봉 칸뿐 아니라 오른쪽 프로파일(봉 전체 합)·레인·현재가·세로 범위가 함께 바뀌고, 테셀레이션 + 제출이 이제 프레임당 1.1~1.7ms 라 얻을 몫이 1ms 안쪽.
**실제로 구현한 것**: 측정해 보니 프레임 시간의 대부분은 칠하기가 아니라 **`web.rs` 가 매 프레임 장면 전체(약 900개 요소)를 비교 하네스용 JSON 으로 만들어 두던 일**이었다(`ui()` 4.8~6.4ms 중 그리기 코드 자체는 약 1ms — 단계별 시각을 찍어 확인). 장면을 그대로 들고 있다가 하네스가 `scene()` 을 부를 때만 JSON 으로 바꾸게 했다(값·좌표 변화 없음 — coords·ops·feed·호버 회귀 그대로). 전·후 수치는 5절 표.
