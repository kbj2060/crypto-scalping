# 대시보드 PWA 웹푸시 알림 (2026-09-04)

사용자 요청: "다른 작업하다가 계속 신호를 놓친다. 데스크톱/폰 알림으로 요약된 정보를 받고 싶다."

## 무엇이 만들어졌나

설치형 PWA + 웹푸시. Chrome/Edge에서 "앱 설치"를 누르면 **자체 창을 가진 데스크톱 앱**이 되고,
창을 닫아도 OS 알림 센터로 알림이 온다. 같은 코드가 안드로이드에서는 그대로, iOS에서는 홈화면
추가 후에 동작한다(사파리 제약 — 탭 상태로는 알림 권한 자체를 못 받는다).

| 파일 | 역할 |

| `scripts/live_push_notifier_20260904.py` | 무엇을 언제 보낼지 판단하는 데몬 |

| `test/test_push_notifier_20260904.py` | 19개 테스트 |

## 설계 판단 세 가지

**1. 의존성 0개로 직접 구현했다.** `pywebpush`를 쓰지 않았다. 이 코드는 `trading_bot.py`가 도는
라이브 서버에서 돌아야 하고, 거기에 패키지를 추가하는 것은 그 자체로 운영 단계다. 대신 손으로 짠
암호화가 틀리면 **조용히** 실패한다는 위험을 진다 — 푸시 서비스는 201을 주고 브라우저만 복호화에
실패하므로 "알림이 안 온다"와 구분되지 않는다. 그래서 `selftest_rfc8291()`이 RFC 8291 5절 예제를
**바이트 단위로** 재현한다. 그게 통과하면 암호화는 정의상 맞고, 남은 실패 경로(전송·VAPID)는
4xx로 시끄럽게 실패한다.

**2. 별도 데몬이다.** 대시보드 서버는 **조회가 있을 때만** 신호를 계산한다
(`load_evidence_signals()`의 60초 TTL 캐시). 즉 아무도 안 보고 있으면 — 정확히 알림이 필요한 그
상황에서 — 트리거가 될 계산 자체가 돌지 않는다. 데몬은 계산을 새로 하지 않고 로컬 대시보드 API를
폴링한다. **알림 숫자와 화면 숫자가 반드시 같아야 하기 때문**이다(같은 공식을 두 군데서 계산하면
언젠가 갈라지고, 그때 어느 쪽이 맞는지 알 수 없다). 부수효과로 캐시가 데워져 폰 접속이 빨라진다.

**3. 발동 감지는 `*_last_fired_ts`로 한다. `*_fired`가 아니다.** ⚠️ **이 기능에서 가장 깨지기 쉬운
지점이다.** payload의 `bottom_fired`/`top_fired`는 sustain window(신호별 8~72봉) 동안 계속 True다.
그걸로 알림 key를 만들면 **사건 하나에 최대 72번** 발송된다. `test_push_notifier_20260904.py`의
`SustainWindowTrapTests`가 이걸 막는다. 반대로 **다이제스트는 `*_fired`가 맞다** — 다이제스트는
"사건이 방금 일어났다"가 아니라 "화면이 지금 이렇다"를 요약하고, 화면 칩도 같은 규칙으로 켜진다.

## 티어

| 티어 | 내용 | 표현 |
|---|---|---|
| T1 | 섀도우/라이브 포지션 개시·종료, 운영 헬스 이상 전환 | 소리 O, 누를 때까지 유지 |
| T2 | net_score \|≥3\|, 청산 버스트, 세션 변동성 창, 경제지표 임박 | 무음, 30분 쿨다운 |
| 다이제스트 | 발동 신호 집합/레짐/포지션 수가 직전 발송과 달라졌을 때 | 무음, 최소 15분 간격, 이전 것을 대체 |

⚠️ **T2와 다이제스트는 매매 트리거가 아니다.** 증거신호 8종은 ETH/BTC/XRP 전부에서 경제성 게이트를
전수 실패했다(`docs/homer/README.md` 5.21절). 알림 문구를 일부러 서술형으로 쓴 이유가 이것이다 —
푸시로 오면 "뭔가 해야 한다"는 압력이 생기고, 검증되지 않은 신호가 그렇게 사실상의 매매 트리거가
되는 것이 이 기능의 가장 큰 위험이다.

## 재시작 폭주 방지 (2겹)

1. **최초 실행은 현재 상태를 기준선으로 기록만 하고 아무것도 보내지 않는다.** 실측: dev 데이터에서
   첫 사이클에 42건이 잡혔다 — 이 장치가 없으면 데몬을 껐다 켤 때마다 42개가 쏟아진다.
2. 그 이후에도 **30분보다 오래된 사건은 seen 처리만 하고 보내지 않는다.** 데몬이 6시간 죽어 있었다면
   복구 시점에 필요한 것은 그동안의 전부가 아니라 "지금"이다.

## 배포 절차

```bash
# 1. 서버 .env에 VAPID 키 생성 (키는 서버에서 만들어지고 저장소에 남지 않는다)
bash scripts/ops/handoff.sh launch server push_vapid --sync scripts/ops/push_vapid_env_apply_20260904.sh \
  -- bash /home/llewyn/crypto-scalping/scripts/ops/push_vapid_env_apply_20260904.sh

# 2. 코드 커밋 -> main 머지 (머지 전 반드시)
bash scripts/ops/check_deploy_drift.sh

# 3. 대시보드 재시작(새 .env를 읽어야 /api/push/config가 enabled=true), 그 다음 데몬 기동
bash scripts/ops/supervisor_push_notifier.sh   # crontab @reboot 등록 권장

# 4. 검증
curl -s https://<대시보드>/api/push/config      # enabled: true 확인
ss -ltn | grep 8787                            # 대시보드 살아있는지 (watcher 로그만 믿지 말 것)
```

브라우저에서: 대시보드 우상단 **🔔 알림 끔** 버튼 → 권한 허용 → **테스트 알림이 즉시 한 번 온다**.
그게 보이면 끝이다. 옆에 뜨는 **앱 설치** 버튼으로 데스크톱 앱으로 만들 수 있다.

⚠️ VAPID 키를 다시 만들면 **기존 구독이 전부 무효**가 되어 모든 기기가 버튼을 다시 눌러야 한다.
`push_vapid_env_apply_20260904.sh`는 키가 이미 있으면 아무것도 하지 않는다.

## 알아둘 것

- `sw.js`와 manifest는 `add_static`이 아니라 no-cache 전용 라우트로 서빙한다. 2026-09-01에 이
  대시보드는 Cloudflare 엣지 캐시 때문에 배포가 안 먹은 전례가 있고, 낡은 서비스워커는 등록된 채
  남아 알림 동작을 계속 지배한다(app.js처럼 `?v=` 캐시버스터를 붙일 수도 없다 — 등록 URL이 바뀌면
  브라우저가 다른 워커로 취급한다).
- 서비스워커는 **일부러 캐싱을 하지 않는다.** 이 대시보드의 모든 숫자는 실시간 시장 상태고, 캐시된
  셸 + 실패한 fetch = 낡은 가격이 자신 있게 표시되는 화면이다. 명백한 에러보다 나쁘다.
- 데몬은 대시보드가 죽어 있으면 빈 dict로 degrade하고 다음 주기에 재시도한다. 크래시 루프가 되지 않는다.
