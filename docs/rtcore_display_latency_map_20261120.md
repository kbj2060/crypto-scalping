# 화면 칸별 지연 지도 — «거래소에서 일이 생긴 순간 → 화면에 보이기까지» (2026-11-20)

읽기 전용 조사(코드만 읽음 · 실행·서버 접속·측정 없음). 배경: `docs/rtcore_design_20261120.md` §1·§5. 목적: 묻는 방식(폴링)을 밀어 주는 방식(푸시)으로 바꿀 순서를 정한다.

## 0. 읽는 법

- **R** = 브라우저 ↔ 서버(Cloudflare 터널) 왕복. 코드 주석의 «~100ms»(server.py `api_stream` 도크스트링)를 쓴다. **실측 아님**(M0 `client_timing` 이 재는 중).
- **최악 지연** = 각 단계의 «기다릴 수 있는 최대 시간»을 더한 값. 계산식을 같이 적었다. 평균이 아니다. 값은 전부 코드 상수에서 옮겼고, 코드로 확정 못 한 단계는 **«미확인»** 으로 두고 합계에서 `+?` 로 표시했다.
- SSE = 서버가 연결 하나로 계속 글을 보내는 방식(Server-Sent Events). WS = 웹소켓. REST = 한 번 묻고 한 번 답받는 요청. swr = 서버가 «묵은 값을 먼저 주고 뒤에서 새로 계산»하는 캐시(`swr_cached`) — **구현은 읽지 않았다(미확인)**.
- 계좌 값·키·개인 정보는 쓰지 않았다.

## 1. 허브 `tick()` 이 각 묻기를 어떻게 양자화하나 (질문 3)

- 허브: `setInterval(tick, POLL_MS)`, `POLL_MS = 500` (app.js:16, 11612). 한 번 틱에 `refreshXxx()` 수십 개를 부른다(app.js:11553~11601). 각 함수는 자기 게이트 `if (now - last < G) return;` 으로 건너뛴다.
- 틱이 0·500·1000… ms 에만 오므로 **실제 간격은 게이트를 500의 배수로 올린 값**이다.

| 게이트 G(코드) | 실제 간격 | 비고 |
|---|---|---|
| `FOOTPRINT_POLL_MS=400` (app.js:145, 게이트 6580) | **500ms** | 400 은 의미 없음. 응답이 500ms 넘으면 `footprintInFlight`(6576)로 더 늘어남 |
| `SUPPLY_1S_POLL_MS=250` (185) | 500ms(틱) / 250ms(자체 `setInterval` 11613) | **스트림이 죽었을 때만** 쓰임. 평소엔 `liveStreamOn()` 이 건너뜀(4611) |
| 1000 (`MARKET_CTX_POLL_MS` 5925, `SITUATION_POLL_MS` 1568, 히트맵 `flowHeatmapPollMs` 1601) | 1000ms, **타이머가 1ms 라도 일찍 오면 1500ms** | 코드 주석(app.js:10~13)에 «실측 간격이 0.5/1.0초로 튀었다» 기록 있음 |
| 2000 (`LIQ_5M_TAIL_POLL_MS` 3204, `SR_LEAN_POLL_MS` 5619) | 2000(드물게 2500) | |
| 5000 (ob5m 6669) · 10000 (`BINANCE_ACCOUNT_POLL_MS` 1637) · 15000(OI 5분 1565) · 30000(청산맵 1660, 위험 레이더 5705) | G 또는 G+500 | |

⇒ 1초 안팎 게이트의 최악은 G+500. `now - last < G - 50` 처럼 여유를 주면 +500 이 사라진다(§6 «덤»).

## 3. 질문 1 — 체결이 났을 때 화면의 계좌·포지션·주문 상태는 언제 바뀌나

**계좌·포지션·미실현 손익·손절/익절 선: 서버가 사용자 스트림 알림을 받으면 화면으로 «밀어 주는 길»이 있다. 단, 신호만 밀고 값은 화면이 다시 받으러 간다.** 함수 경로:

1. 바이낸스 사용자 데이터 WS → `orders.py::_user_stream_run` (receive 2980) → `user_event_kind` (617). `ORDER_TRADE_UPDATE` 의 `x ∈ {TRADE, CALCULATED}` 와 `ACCOUNT_UPDATE` 만 `"fill"`. 취소·만료·`AMENDMENT` 는 `"order"`(계좌는 안 읽음), 새 주문 `NEW` 는 무시(617~628).
2. `kind == "fill"` → `acct_dirty.set()` (3005). 모든 알림은 `wake_fills()` (3003) 로 서버의 대기 루프·감시 틱을 깨움.
3. `account_refresher` (3017~3034): `acct_dirty` 대기 → **0.3초 합치기** → `produce_account` REST 로 계좌 재조회 → 캐시 `binance_account_cache["payload"]` 교체 → **`user_stream["seq"] += 1`** (3030) → `wake_fills()` → `ACCOUNT_PUSH_GAP_S=3.0` 쉼.
4. `acct_seq=lambda: user_stream["seq"]` (3050) → `server.py::publish_dashboard_events` 가 **1초 루프**마다 `"acct_seq"` 를 `/api/events` 메시지에 실음(3517), 클라이언트마다 큐 1칸(가득 차면 옛 것 버림 — 번호가 올라가기만 해서 안전).
5. 화면 `connectDashboardEvents` → `applyDashboardEvent` (2244): `acct_seq` 가 직전 값과 다르면 `refreshBinanceAccount(true, false)` (2255~2257) → `/api/binance-account` (`fresh` 없이 = 방금 갱신된 서버 캐시를 바로 받음) → `renderBinanceAccount` (2948) → 계좌 카드 + `renderSnapshotChart()` + 청산 버튼 동기화.

**주문 상태(진행 중·대기·체결 결과)는 밀어 주는 길이 없다.** 서버 쪽은 알림으로 즉시 깨어 상태를 고치지만, 화면은 `manualEntryPollStatus`(진행 중 1.5초) / `manualWaitPoll`(대기 살아 있는 동안 3초)로 **묻는다**. 대기가 끝난 것을 알아채면 그때서야 `refreshBinanceAccount(true)` 를 부름(13127).

주의(코드에서 보이는 구멍):
- 첫 `acct_seq` 는 기준만 잡고(`lastAcctSeq == null`), 연결 시 첫 메시지(`initial_payload`)에는 `acct_seq` 가 없다(server.py:3624).
- 연속 체결에서 직전 조회 후 3초 안의 알림은 **다음 조회가 최대 3초 늦다**(코드 주석: IP 한도 2,400/분 대비 조회 1회 무게 ≈ 50).
- 알림 정상 여부는 응답의 `user_stream.connected / last_event_age_s` 로만 보임(orders.py:813). 알림이 끊기면 10초+10초 길로 물러난다(화면에는 따로 표시 안 함 — **미확인**).

## 4. 질문 2 — 풋프린트의 역할 분담

- **직접 경로(주된 길)**: 브라우저가 `@trade` 를 직접 받아 `footprintLiveAdd` 로 가격 칸(`roundHalfEven` 으로 서버 반올림 규약과 맞춤)에 쌓고, 100ms 안 같은 방향·연속 체결 ID 를 한 주문으로 묶어 고래/리테일 칸도 계산한다(서버 `TakerOrderAggregator` 거울). 칠하기는 두 갈래: 형성 봉만 rAF 부분 칠(≈프레임당 1회, 조건 `fpCv.live()`), 아니면 전체 렌더 게이트 **400ms**.

- 실제 갱신 간격 요약: 형성 봉 칸 숫자 = 체결마다(최대 프레임당 1회 ≈ 16.7ms@60Hz) 또는 400ms / 서버 값 경로 = 500ms.
