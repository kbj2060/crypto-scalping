## 격리 원칙 (실행 전 확인)

프로덕션 `data/live/*.duckdb`는 라이브 봇이 쓰기 중인 파일이라 전혀 건드리지 않았다.
신규 격리 DB `data/research/ws_e_orderbook_raw_pilot.duckdb`에만 기록. 실제 프로덕션
`orderbook_recorder.py`에 원시 레벨 저장을 배선하는 것은 **봇 재시작이 필요한 별도의
운영 변경**이라 이번 세션에서 하지 않았다 (안전 규칙상 명시적 승인 필요 사항).

## 실행 내용 — ETH/USDT 선물 실제 거래소에서 6분 파일럿 캡처

**중요한 설계 이탈 명시**: 설계 문서의 T-E2는 72시간 소크테스트를 요구하지만, 이번
세션에서는 **6분(360초) 파일럿**만 실행했다. 메커니즘이 올바르게 동작하는지 확인하는
용도이며, 72시간 커버리지/안정성 수락 기준을 충족했다고 주장하지 않는다.

## T-E1 Round-trip 자가검증 — **통과**

36개 캡처 전체에서 `bids_json`/`asks_json` 원시 레벨로부터 재계산한
`bid_notional_{1,5,10,20}`, `ask_notional_{1,5,10,20}`, `imbalance_{1,5,10,20}`이
저장된 요약 컬럼과 **불일치 0건** (rel err < 1e-9 기준). 저장 로직이 스스로를
검증하는 설계 의도대로 동작함을 확인.

## T-E2 간격/커버리지 (짧은 파일럿 기준)

| 지표 | 값 | 설계 기준(72h) |
|---|---|---|
| 목표 대비 캡처 수 | 36/36 (100%) | ≥95% |
| 간격 p50 | 10.00초 | — |
| 간격 p99 | 11.55초 | ≤15초 (통과) |
| 최대 간격 | 11.62초 | — |
| 오류 | 0건 | — |

6분 규모에서는 목표 간격을 안정적으로 지켰다. **72시간 연속 운영, 봇 지연 회귀 테스트,
DuckDB 락 경합 테스트는 미실행** — 실제 프로덕션 배선 전 반드시 필요.

## 판정

- **T-E1 (round-trip): PASS** — 신뢰성 있게 완결.
- **T-E2 (72h 소크): 미검증** — 짧은 파일럿은 통과했으나 설계 문서의 수락 기준
  (72시간, 봇 지연 회귀, 락 경합 0건)은 이번 세션에서 검증 못 함.
- BTC/SOL 지속 수집(T-E4)과 저장소 성장(T-E5)은 기존 프로덕션 파이프라인이 이미
  가동 중이므로 별도 실행 불필요 (WS-D의 D4 결과가 실측 자료).

## 후속 조치 (프로덕션 배선 전 필수)

1. 이 파일럿 스크립트의 로직(요약 계산 + 원시 JSON 병행 저장)을
   `orderbook_recorder.py`에 통합하되, **신규 컬럼 추가로만** (기존 스키마 불변 원칙).
2. 프로덕션 배선은 봇 재시작을 수반하므로 사용자 승인 후 별도 세션에서 진행.
3. 배선 후 실제 72시간 소크테스트로 T-E2 수락 기준 재검증.
4. 데이터 에폭 경계 문서(`docs/feature_contract_manifest.json` 또는 신규
   `data_epochs.json`)에 원시 레벨 저장 시작 시점 기록 — 아직 미생성.
