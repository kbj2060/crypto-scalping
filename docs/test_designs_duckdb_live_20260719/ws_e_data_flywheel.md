# WS-E 테스트 설계도 — 데이터 플라이휠 확장 (수집 무결성/성능 수락 테스트)

성격: 수집 파이프라인 변경의 **수락 테스트**. 모델/가설 없음.
공수: 반나절 구현 + 1주 시운전. 선행 조건 없음. **가장 먼저 실행** (오늘 심어야 3~6개월 뒤 수확).

## 변경 항목 (상위 설계 WS-E)

1. E1: 원시 L2 상위 20레벨 `bids_json`/`asks_json` 저장 (기존 요약과 병행)
2. E2: 10초 고정 주기 연속 스냅샷 테이블 신설 (의사결정 조건부 샘플링과 별도)
3. E3: 체결 테이프 1m 집계 확장 (방향별 체결 규모 히스토그램)
4. E4: BTC/SOL 수집 지속 + 3개월 체크포인트
5. E5: 저장소 성장/유지보수 정책

## 설계 제약

- **기존 테이블 스키마 불변.** 신규 컬럼은 신규 테이블 또는 ALTER TABLE 추가 컬럼으로만.
  (decision_feature_frame 스키마 하드체크 사고 전례 — 스키마 변경은 auto-migrate 경로 필수.)
- 라이브 봇 경로에 지연 추가 금지: 신규 기록은 기존 recorder처럼 executor 스레드 +
  `serialized_duckdb_access` 경유.
- 실주문 경로와 무관 (BINANCE_ACCOUNT_ENABLED 상태와 독립).

## 수락 테스트

### T-E1. 원시 레벨 저장 — 자기검증 (round-trip)
핵심 아이디어: **원시 레벨에서 요약 통계를 재계산하면 기존 요약 컬럼과 일치해야 한다.**
저장 로직 자체가 스스로를 검증한다.

1. 신규 컬럼: `bids_json`, `asks_json` (상위 20레벨 [price, qty] 배열, JSON VARCHAR).
2. 검증 잡: 최근 24h 행 전수 — `bids_json`에서 `bid_notional_{1,5,10,20}`,
   `imbalance_*`, `microprice` 재계산 → 저장된 요약 컬럼과 rel err < 1e-9 일치.
3. **수락 기준**: 불일치 0건 (1건이라도 있으면 직렬화 순서/타입 버그).
4. 용량 체크: 행당 추가 바이트 실측 → 일간 증가량 보고 (예상: 20레벨×2×~25B ≈ 1KB/행,
   스로틀 2s 유지 시 무해 — 실측으로 확인).

### T-E2. 10초 연속 스냅샷 — 커버리지/간격 테스트
1. 신규 테이블 `orderbook_periodic_snapshots` (+`_btc`/`_sol` — **자산별 테이블 분리**,
   자산 혼합 버그 전례). 스키마는 decision_snapshots와 동일 + `bids_json/asks_json`.
2. 시운전 72h 후 검증:
   - 간격 분포: 연속 행 간 Δt의 p99 ≤ 15초, 최대 gap 목록 보고 (재연결 구간 식별).
   - 커버리지: 기대 행수(8,640/일) 대비 실측 ≥ 95%.
   - `exchange_timestamp` 단조성 + 로컬 시각과의 skew p99 < 2초.
3. 봇 영향 회귀 테스트: 시운전 전/후 각 24h의 봇 의사결정 루프 지연 로그 비교 —
   중앙값 증가 < 10ms, p99 증가 < 100ms.
4. 락 경합: 시운전 중 `database is locked`/재시도 로그 0건.

### T-E3. 체결 테이프 확장 — 보존 검증
1. `microstructure_1m`에 방향별 체결 규모 히스토그램 컬럼 추가
   (예: `buy_notional_hist_json`, `sell_notional_hist_json`, 고정 로그 스케일 bin).
2. 검증: 히스토그램 합계 = 기존 `recent_trade_notional`류 집계와 정합 (rel err < 1e-6,
   윈도 정의 차이는 문서화).
3. 스키마 추가는 auto-migrate 경로(ALTER TABLE) 사용 — 마이그레이션 후 구행 null 처리
   규칙 명시, 삽입 실패 0건 48h 확인.

### T-E4. BTC/SOL 누적 체크포인트
- 검증 항목(월 1회): 테이블별 최신 ts 나이, 월 커버리지 ≥ 95%, 자산 라벨 교차 오염 0건
  (BTC 테이블의 mark_price 범위가 BTC 가격대인지 등 sanity bound).
- **모델 학습 해금일: 2026-10-14** (3개월 누적). 그 전 학습 시도는 리뷰에서 반려.

### T-E5. 저장소 성장/유지보수
1. 신규 수집 활성 후 7일간 각 DB 파일 크기 일간 기록 → 월간 성장률 외삽 리포트.
2. 판정 기준: microstructure.duckdb 월 성장 < 5GB면 현행 유지. 초과 시 파티셔닝
   (월별 파일 분리) 설계 발동.
3. 백업 정책 확인: `data/live/backups` 주기·보존 개수 확인, 신규 테이블 포함 여부 검증
   (백업본 열어서 신규 테이블 존재 + 행수 > 0 확인).
4. 월 1회 유지보수 잡에 `CHECKPOINT` + 파일 크기 로그 포함.

## 데이터 에폭 경계 기록 (필수)

신규 컬럼/테이블은 백필 불가능하다. `docs/feature_contract_manifest.json` 또는 신규
`data_epochs.json`에 다음을 기록:

```
raw_l2_levels:        ETH 2026-07-XX~, BTC/SOL 2026-07-XX~
periodic_snapshots:   2026-07-XX~
trade_histograms:     2026-07-XX~
```

이후 모든 연구는 에폭 경계 이전 구간에 해당 피처를 요구하면 안 된다
(silent truncation 전례 — 파생 아티팩트 5종 동시 연장 규칙과 동일 계열의 함정).

## 전체 수락 기준 (완료 판정)

1. T-E1 round-trip 불일치 0건 (24h).
2. T-E2 커버리지 ≥95%, 봇 지연 회귀 통과, 락 경합 0건 (72h).
3. T-E3 정합 검증 + 삽입 실패 0건 (48h).
4. 에폭 경계 문서화 완료.
5. WS-D의 D4 수집 건강 감시에 신규 테이블 편입.
