# 실시간 코어(rtcore) 설계 — 주문·화면 표시 지연 줄이기 (2026-11-20)

## 0. 사용자 결정

- 최종 목표: **실시간 데이터를 최대한 빨리 보고, 주문이 최대한 빨리 들어가는 것.** 주문 경로와 화면 표시 둘 다 대상이다.
- 파이썬·자바스크립트의 실시간 경로를 다른 언어로 바꾸고, 알고리즘 최적화·리팩토링을 같이 한다.
- **주문은 지정가(메이커, post-only GTX)로 설계한다. 시장가 경로는 새로 설계하지 않는다.**
- 안드로이드 앱(`docs/android_app_design_20261120.md`, 다른 브랜치)은 이 최적화가 끝날 때까지 보류. 그동안 API 모양·주소·스트림 형식은 바꿔도 된다.

### 질문지 답 (2026-11-21 새벽 · 24문항 중 1~8 · 사용자가 직접 고름)

이미 있는 시장가 분기는 «새 설계»가 아니므로 아래 답대로 둔다(분기 번호는 `docs/rtcore_order_rules_inventory_20261120.md`).

| # | 항목 | 답 | Rust 에서 할 일 |

## 1. 기준선 (실측)

서버 `data/live/dashboard_external.log` 의 `plan_timing` 30,661줄(2026-11-11~11-20).

| 구간 | 값 | 표본 |
|---|---|---|
| 진입 계획 조립 | 중앙 102ms · 상위 10% 208ms · 상위 1% 2,231ms · 최대 27,392ms | 30,591건 |
| 청산 계획 조립 | 중앙 377ms · 상위 10% 539ms · 상위 1% 1,244ms | 70건 |
| 서버 → 바이낸스 호가 조회 1회 | 중앙 41ms · 상위 1% 533ms | 30,661건 |
| 손절·익절 감시 주기 | 2초(`watch_brackets`) | 코드 |
| 따라가기 재호가 판단 주기 | 3초(`POLL_SEC`) | 코드 |
| 화면: 가격 | 0.08초마다(브라우저 → 바이낸스 직접) | 코드 |
| 화면: 수급 / 풋프린트 / 상황·시장 맥락 / 계좌 | 0.25초 밀기 / 0.4초 / 1초 / 10초 묻기 | 코드 |

느린 계획(1초 이상)에서는 서로 무관한 단계(바이낸스 조회와 서버 안 계산)가 같은 시간만큼 같이 늦는다. 대시보드 프로세스(asyncio 루프 하나가 수집·계산·응답·주문을 모두 처리)가 멈춘 모양이다. **원인은 미확정 — M0 에서 잰다.**

재지 못한 것: 브라우저 → 서버(Cloudflare 터널) 구간, 화면 한 장 그리는 시간, 누른 순간 → 거래소 접수 전체 시간.

## 2. 범위

**바꾼다**
- 실시간 수신·메모리 상태·화면으로 밀기 → Rust 새 프로세스 `rtcore`.
- 주문 계획·지정가 집행·손절/익절 감시 → `rtcore` (그림자 대조와 가짜 거래소 시험을 통과한 뒤).
- 화면 → Rust(egui) 웹어셈블리. 앱과 한 코드. 1920 폭 시제품으로 먼저 확인.

**안 바꾼다**
- 연구 스크립트, 예측 모델 워커(파일로 결과를 쓰는 지금 방식 유지), 저장용 수집기, 느린 카드(거시·옵션·뉴스) — 실시간 경로가 아니다.
- **재호가 판단 주기 3초.** 10-18 시뮬(`scripts/research_eth_peg_repeg_delay_20261018.py`)에서 바꿀 근거가 없었다. 3초보다 짧은 주기는 검증된 적이 없으므로 이 설계에서 건드리지 않는다(바꾸려면 따로 사전등록).
- 시장가 관련 기존 동작(120초 뒤 잔량 처리, 스위칭, 손절 발동 시 집행)은 **새로 설계하지 않고**, M3 전에 «그대로 옮김 / 뺌»을 사용자에게 묻는다. 목록은 주문 규칙 목록 문서에 모은다.

### 전환 규칙 (사용자 지시 2026-11-20 저녁)

«다른 것들도 Rust 로 바꿨을 때 성능은 그대로이고 속도가 조금이라도 빨라지면 Rust 로 진행.» 위 «안 바꾼다» 중 실행 경로에 있는 것은 아래 기준으로 **하나씩 판정**해 옮긴다. 판정은 실측으로만 한다.

| 대상 | «성능 그대로» 확인 | «빨라짐» 확인 | 지금 판정 |
|---|---|---|---|
| 실시간·주문 코어 | 그림자 대조·가짜 거래소 불변식(§7) | M0 기록 | 진행(확정) |
| 화면에 닿는 수신(체결·호가·청산·OKX·Bybit·미결제약정) | 같은 입력을 재생해 파이썬 계산과 값 일치 | 수집기 디스크 주기(5~10초)가 사라짐 | 진행 — 1초 수급부터 |
| 대시보드 응답 서버(느린 카드 JSON) | 응답 본문 일치 | 서버 처리 시간 중앙값 | 코어 병행 가동 뒤 |
| 화면(자바스크립트) | 같은 자료·같은 칸 수를 그림 | egui 한 장 그리는 CPU 시간이 지금(풋프린트 중앙 9~11ms)보다 짧은가 | **«빨라짐» 통과(시제품 · 아래 진행 기록 3)** — 진행. «성능 그대로»는 카드마다 옮길 때 확인 |
| 저장용 수집기 | 같은 구간 행 수·값 일치(그림자 7일) · 전진 검정 기록이 끊기지 않을 것 | 쓰기 지연 | 코어가 받는 스트림부터 순서대로 |
| 예측 모델 워커(서빙만 · 학습은 파이썬) | 예측값 일치(1e-6) · 승격 게이트 대상은 기존 계약 그대로 | 계산 시간 | 마지막 순서 |
| 연구 스크립트 | — | — | 대상 아님(실행 경로가 아니다) |

빨라지지 않거나 값이 달라지면 그 대상은 옮기지 않고 근거를 남긴다.

## 3. 구조

```
바이낸스 웹소켓(체결·호가·마크가격·강제청산·계좌 알림)
        │
   ┌────▼─────────────────────────────┐
   │ rtcore (Rust, tokio, 127.0.0.1:8788) │
   │  feed   수신·재연결·순서 확인       │
   │  state  코인별 메모리 상태          │
   │  hub    화면 연결로 밀기(웹소켓)    │
   │  order  계획·지정가 집행·감시 (M2~) │
   └────┬─────────────────────┬───────┘
        │ 밀기                  │ 서명 주문
     브라우저·앱              바이낸스

파이썬(그대로): 모델 워커 → data/live/*.json → 옛 서버(8787) → 느린 카드
```

- `rtcore/` 는 저장소 루트의 Cargo 크레이트 하나로 시작한다. `proto`(주고받는 메시지 형)는 tokio 에 기대지 않는 모듈로 두어, 나중에 화면 쪽이 그대로 가져다 쓴다.
- 옛 서버와 `rtcore` 는 M3 까지 나란히 돈다. 느린 카드는 옛 서버가 계속 낸다.
- 전송은 웹소켓 + JSON 으로 시작한다. `ponytail:` 압축·이진 형식은 측정으로 필요가 확인되면 바꾼다.
- 모든 메시지에 시각 셋을 싣는다: 거래소 사건 시각 · 코어 수신 시각 · 코어 송신 시각. 화면이 «사건 → 그림» 지연을 스스로 잰다.

## 4. 주문 경로 (지정가)

지금: 누름 → 계획 조립(바이낸스에 호가·펀딩·변동성·환산비 조회) → 지정가 접수.

바꿀 것
1. **계획 입력을 받아 둔 값으로.** 호가는 웹소켓 최신값, 펀딩·변동성·환산비·필터·수수료는 코어가 주기적으로 갱신해 둔 값. 값마다 나이를 재고, 한도를 넘게 낡았으면 지금처럼 새로 묻는다(낡은 값으로 조용히 내지 않는다).
2. **포지션·미체결은 계좌 알림으로 유지.** 청산 계획이 계좌를 새로 읽지 않는다. 알림이 끊긴 것이 확인되면 새로 읽는 옛 방식으로 돌아간다.
3. **주문 연결을 따로 유지.** 화면 응답·수집과 주문이 같은 실행 줄을 쓰지 않는다.
4. **미리보기와 실주문은 계속 같은 함수 하나**를 지난다(지금 규약 유지).

안 바꿀 것: 2단 확인(POST·confirm=1·게이트), 상한 계산, 헤지 모드 규칙, GTX 거부 처리, «나갔는지 모르는 주문» 처리, 재호가 전 취소 확인(`ensure_closed`), 재시작 고아 주문 정리, 재호가 3초.

목표: 누른 뒤 코어가 쓰는 시간 중앙 5ms 이하 · 상위 1% 50ms 이하(지금 102ms · 2,231ms). 거래소 왕복 41ms 는 남는다.

## 5. 화면 표시 경로

1. 묻는 방식을 없앤다. 체결·호가·풋프린트 칸·수급·상황·계좌·포지션·주문 상태를 코어가 연결 하나로 민다.
2. 풋프린트·수급처럼 누적하는 칸은 «처음 한 번 전체 + 이후 바뀐 것만».
3. 화면은 받은 즉시 다음 그리기에 반영한다. 그리기는 화면 주사율에 맞추고, 숨은 탭은 연결을 닫는다(지금 규칙 유지).
4. 화면 코드는 egui 웹어셈블리로 옮긴다. 옮기기 전까지는 지금 app.js 가 새 연결을 구독하도록 얇게 고친다(M1) — 화면 재작성 전에 표시 지연부터 줄인다.

목표: 거래소 사건 → 코어 송신 중앙 5ms 이하. 계좌·포지션 반영 10초 → 체결 알림 즉시.

## 6. 손절·익절 감시

- 2초 주기 → 체결이 들어올 때마다 검사(같은 1초 가격 원천 규칙·같은 판정식).
- 감시가 코어로 넘어가는 M3 가 가장 위험한 전환점이다. 넘기기 전 조건: 코어와 옛 감시가 같은 입력에 같은 발동을 내는지 그림자 대조 7일 · 코어가 죽으면 옛 감시가 이어받는 길.
- 거래소에 손절 주문을 직접 거는 것은 사용자 선택 사항으로 남긴다(이 설계는 지금의 서버 감시 방식을 옮긴다).

## 7. 단계와 통과 기준

| 단계 | 내용 | 통과 기준 |
|---|---|---|
| M0 측정 | 누름→접수 단계별 기록 · 프로세스 멈춤 감지(멈춘 순간의 스택) · 화면 왕복·그리기 시간 보고 | 기록이 서버 로그에 남고 기존 시험이 그대로 통과 · 주문 동작 불변 |
| M1 코어 읽기 전용 | 수신·상태·밀기 · 옛 서버와 나란히 | 가짜 거래소 시험 통과 · 실서버 병행에서 옛 서버 값과 일치 · 사건→송신 중앙 5ms 이하 |
| M2 계획 그림자 | 코어가 같은 입력으로 계획을 계산해 옛 계획과 대조(실주문은 옛 경로) | 7일 동안 수량·가격·상한·거절 사유 불일치 0건(분모 병기) |
| M3 집행·감시 전환 | 지정가 집행·손절 감시를 코어로 | 가짜 거래소 불변식(총 체결 ≤ 계획 · 살아남은 지정가 ≤ 1 · 항상 종료 상태) + 실패 주입 통과 · 사용자 승인 뒤 전환 |
| M4 화면 | egui 웹 시제품(1920 폭 풋프린트 한 장) → 카드별 이전 | 시제품: 한글 선명도·배치·그리기 시간을 사용자가 확인 |

각 단계의 «빨라졌다»는 M0 기록의 같은 지표로만 말한다.

## 8. 안전 규칙

- **실주문 시험 금지.** 주문 경로는 가짜 거래소(`test/test_manual_peg_execute_invariants_20260913.py` 방식)로만 시험한다.
- 개발기에서 바이낸스에 접속하지 않는다(서버와 IP 한도 공유). 코어 시험은 녹화한 메시지·가짜 서버로만.
- 개발기에서 대시보드 서버를 띄우지 않는다(워크트리 `.env` 에 실키가 있을 수 있다).
- 배포는 커밋 → `check_deploy_drift.sh` → 푸시 순서, 사용자 승인 뒤. 에이전트는 커밋·푸시·서버 접속을 하지 않는다.
- 공개 저장소다. 계좌 값·키·개인 이메일이 든 파일은 커밋하지 않는다.

**바뀌지 않는 원칙**
- 대상마다 «값·기능 그대로»를 시험이나 그림자 대조로 보인 뒤에만 옛 것을 끈다. 못 보이면 끄지 않는다.
- 옛 파이썬·자바스크립트는 새 것이 통과할 때까지 그대로 돈다(나란히 → 대조 → 전환 → 옛 것 삭제).
- 실주문 시험 금지 · 개발기에서 거래소 접속 금지 · 주문 전환은 사용자 승인 뒤(§8).
- 주문은 지정가로만 설계한다. 기존 시장가 분기 13곳은 전환 전에 사용자에게 묻는다.
- 전진 검정이 걸린 수집·기록은 끊기지 않게 한다(그림자 기간 동안 두 벌 기록).
- 모델은 학습을 파이썬에 둔다(연구). 서빙만 옮기고 예측값 일치(1e-6)를 보인다. 승격 게이트 대상은 기존 계약 그대로.
