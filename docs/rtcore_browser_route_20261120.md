# 브라우저 → rtcore 접속 길 (2026-11-20 조사 · 읽기 전용, 코드·설정 안 건드림)

목표: «거래소 사건 → 화면» 지연을 줄인다. 길에 파이썬 프로세스가 끼면 안 된다(설계 `docs/rtcore_design_20261120.md` §5).
도메인·터널 ID·토큰은 적지 않는다: 호스트는 `<호스트>`.

## 1. 지금 구조 (사실)

```
브라우저/휴대폰 ──https──> Cloudflare 가장자리 ──(Access: 로그인/정책)──> 터널 ──> cloudflared(서버)
                                                                              │
                                                                 http://127.0.0.1:8787 (파이썬 aiohttp, 옛 대시보드)
                                                                              ├ 정적 /dashboard/live/*
                                                                              ├ /api/* (약 70개)
                                                                              ├ /api/stream (SSE, 수급·상황)
                                                                              └ /api/events (SSE, 상태)
rtcore (Rust) ── 127.0.0.1:8788 평문 웹소켓 ── 바깥에서 닿는 길 없음(이 문서가 정할 것)
```

- 터널은 **토큰으로 띄우는 이름 붙은 터널**이다: `cloudflared tunnel --no-autoupdate --url <원본> run --token-file <파일>` (`dashboard/scripts/start_cloudflare_tunnel.sh` 줄 70 부근). 토큰은 `.env` 의 `CLOUDFLARE_TUNNEL_TOKEN` 에서 읽어 600 권한 파일로 쓴다. 감독은 `supervise_cloudflare_tunnel.sh`(죽으면 5초 뒤 재기동), 부팅 때 `start_public_dashboard.sh` 가 둘 다 올린다.
- Cloudflare 문서상 `token`/`token-file` 은 **원격 관리 터널 전용**, `config`(로컬 파일) 은 로컬 관리 전용이다 (https://developers.cloudflare.com/cloudflare-one/connections/connect-networks/configure-tunnels/cloudflared-parameters/). 따라서 **ingress(호스트→포트) 규칙은 저장소에 없고 Cloudflare 대시보드에 있다**(추정이 아니라 위 사실에서 도출; 저장소에 ingress 설정 파일 없음 — `dashboard/` 와 `scripts/ops/` 에서 확인). `--url` 은 원격 관리 터널에서는 무시될 가능성이 높다(추정 · 미확인).
- `dashboard/docs/cloudflare_named_tunnel.md` 줄 12~28: 공개 호스트 이름 → `http://127.0.0.1:8787` 이 «live ingress rule» 이라고 적혀 있다. 호스트가 둘(루트·`dashboard.` 하위)로 안내돼 있으나 실제로 몇 개가 있는지는 모른다. **8787 이외로 가는 규칙은 문서에 없다.**
- 접근 제어: 저장소 코드 어디에도 Access 설정·헤더 검사가 없다(`CF-Access`·`Cloudflare Access` 검색: `supervise_server.sh` 주석 하나뿐). 그 주석(줄 31~36, 2026-09-12): «Cloudflare Access 가 터널 경로를 막았지만 LAN 경로가 열려 있어» 기본 바인드를 `0.0.0.0 → 127.0.0.1` 로 바꿨다. 즉 **Access 는 Cloudflare 쪽에서 걸려 있고, 어느 앱(호스트 전체/경로별)·어떤 정책인지는 저장소로 알 수 없다.** 서버(`dashboard/server.py`)에는 Origin 검사가 없다(`Origin` 검색 결과 없음). 인증은 전적으로 Access 몫이다.
- 서버 쪽 바인드: 대시보드 `127.0.0.1:8787`(`supervise_server.sh` 줄 37). rtcore `127.0.0.1:8788`(`rtcore/src/main.rs` 줄 9, 환경변수 `RTCORE_LISTEN`).

새 rtcore 구독이 따를 규칙(위에서 도출): ①상대 경로·현재 호스트(`location`) 사용, ②숨은 탭이면 닫고 보이면 연다, ③재시도는 5초 이상 간격(막힌 환경에서 틱마다 실패 반복 금지), ④재연결 때 커서/`since` 를 0으로 되돌려 서버 스냅숏으로 다시 시작(rtcore 는 접속 시 스냅숏을 준다 — `hub.rs` 줄 40~53), ⑤`liveStreamOn()` 과 같은 «최근 N초 메시지 수신» 판정으로 SSE·폴링의 대체 경로를 유지(rtcore 가 죽어도 옛 길이 그대로 받는다 — 전환 규칙 «옛 것은 새 것이 통과할 때까지 돈다»).

## 2. rtcore 현재 상태 (사실)
- `hub.rs`: `accept_async` 로 **경로를 보지 않고** 업그레이드를 받는다(줄 36 — 요청 URI 검사 없음). 따라서 `/rt` 로 와도 `/anything` 로 와도 동작한다. 경로 규칙 쪽(가)에는 유리(경로가 안 잘려도 된다), 보안 면에서는 «아무 경로나 받음».
- 인증·Origin 검사·연결 수 제한 없음. 첫 메시지 10초 안에 `{"subscribe":[..]}` 가 없으면 끊는다(줄 40~46). 읽기 전용(주문·계좌·키 없음 — `lib.rs` 줄 1).
- 느린 구독자는 끊는다(큐 16384건, `lib.rs` QUEUE_CAP). 접속자 수 상한 없음.

## 3. Cloudflare 쪽 사실 (공식 문서 열람)
| 사실 | 출처 |
|---|---|
| 웹소켓은 «추가 설정 없이» 프록시된다. 양방향 무전송이 일정 시간 지속되면 닫는다 → 클라이언트 하트비트(ping/pong) 권장. WAF 는 업그레이드 요청만 본다. | https://developers.cloudflare.com/network/websockets/ |
| 로컬 관리 터널 ingress: `hostname` + 선택적 `path`(**정규식**) 로 위에서부터 첫 일치. 경로는 **잘리지 않고 원본에 그대로 전달**. 규칙 끝에 catch-all(`http_status:404` 등) 필수. | https://developers.cloudflare.com/cloudflare-one/connections/connect-networks/configure-tunnels/local-management/configuration-file/ |
| 원격 관리 터널의 «게시된 애플리케이션(Published application)» 은 **Subdomain·Domain·Path(선택)·Service URL** 을 받는다. 경로는 안 바뀌고 전달된다. 경로별로 다른 Service URL 을 둘 수 있다는 것은 문서가 «암시»하는 수준(명시 아님 — **사용자가 대시보드에서 확인 필요**). | https://developers.cloudflare.com/cloudflare-one/connections/connect-networks/get-started/create-remote-tunnel/ |
| Access 앱은 호스트(+선택 경로)에 걸린다. **Path 를 비우면 그 호스트의 모든 경로**를 덮는다. 같은 뿌리 경로에 규칙이 여럿이면 **더 구체적인 규칙이 이기고 상속하지 않는다**. | https://developers.cloudflare.com/cloudflare-one/policies/access/app-paths/ |
| 서비스 토큰: 요청에 `CF-Access-Client-Id` / `CF-Access-Client-Secret` 헤더, 정책 동작은 **Service Auth**(아니면 로그인 화면이 뜸). 엄격 모드(2026-10-05 이후 생성된 조직 기본)에서는 Allow 정책·`CF_Authorization` 쿠키를 무시하고 서비스 토큰 성공 시 쿠키를 발급하지 않는다. **웹소켓 핸드셰이크에 대해서는 이 문서가 말하지 않는다**(핸드셰이크도 일반 HTTP GET 이므로 헤더가 실릴 것으로 «추정» — 시험 필요). | https://developers.cloudflare.com/cloudflare-one/identity/service-tokens/ |

## 5. 권고: (가) 같은 호스트 `/rt` 경로 규칙

이유
1. 길에 cloudflared 외에 아무것도 안 낀다.
2. 같은 오리진이라 **Access 쿠키가 웹소켓에 그대로 실린다** — CORS·Origin·재로그인 문제가 사라진다(나의 핵심 약점).
3. 서버 코드는 거의 안 바뀐다(`hub.rs` 가 이미 경로를 안 본다). 필요한 변경은 Cloudflare 규칙 한 줄 + app.js 한 모듈.
4. 되돌리기 쉽다: 규칙 삭제 → 화면은 옛 SSE 로 계속 돈다.
5. 휴대폰 앱은 같은 호스트·같은 경로를 서비스 토큰 헤더로 쓴다.

경로 이름은 `/rt` 권장(`/api/` 아래로 두면 앞으로 옛 서버로 넘길 때 헷갈림). 정규식은 `^/rt$` 가 정확하다(`^/rt` 는 `/rtx` 도 잡는다).

### 실행 단계
**코드가 할 일 (rtcore, 별도 승인 뒤)**
1. `hub.rs`: 업그레이드 요청 경로가 `/rt` 가 아니면 404 (`accept_hdr_async` 콜백). 지금은 아무 경로나 받는다(줄 36).
2. `hub.rs`: `Origin` 헤더 검사 — 허용 목록(환경변수 `RTCORE_ALLOW_ORIGIN`, 쉼표 구분) 밖이면 403. 브라우저는 Origin 을 위조 못 하므로 **다른 사이트의 페이지가 로그인된 사용자의 쿠키로 웹소켓을 여는 공격(CSWSH)을 막는다**. 앱(비브라우저)은 Origin 이 없을 수 있으니 «Origin 헤더가 있고 목록 밖일 때만 거부».
3. `hub.rs`: 동시 연결 상한(예: 32, 세마포어) — 넘으면 즉시 닫음. 구독자 수와 큐 메모리 곱이 상한이다(16384건 × 연결 수).
4. `hub.rs`: 서버가 30초마다 ping(Cloudflare 유휴 종료 방지). 현재는 보내지 않음.
5. 읽기 전용 구독과 나중의 주문 채널은 **다른 경로·다른 포트**로 둔다(`/rt` 읽기 전용, 주문은 별도 — 아래 6절).

**app.js 가 할 일 (화면 변경이므로 `/impeccable` 대상 아님 — 보이는 모양을 안 바꾸는 연결 변경, 단 CLAUDE.md 규칙 확인 필요)**
6. `ensureRtStream()` 을 `ensureLiveStream`(4727) 옆에 둔다: 같은 호출 지점(11557 틱, 11615 가시성)에 붙이고, 숨으면 닫고, 재시도 5초(4600 선례), `rtStreamOn()`(최근 3초 수신) 이 참이면 SSE·폴링을 쉰다.
7. 처음에는 **그림자 모드**: 화면은 SSE 를 그대로 쓰고 rtcore 메시지의 `tx_us`·`rx_us` 와 수신 시각으로 «사건→화면» 지연만 잰다. 일치·지연이 통과해야 SSE 를 끈다.

**서버 설정**
8. rtcore 상시 가동(감독 스크립트는 기존 `supervise_*.sh` 패턴 — 이 문서 범위 밖). 바인드는 `127.0.0.1:8788` 유지(`0.0.0.0` 금지 — 2026-09-12 사고와 같은 이유).

**사용자가 Cloudflare 에서 직접 할 일**
9. 대시보드 Zero Trust → 해당 터널 → 게시된 애플리케이션: `<호스트>` + Path `^/rt$` → `http://127.0.0.1:8788` 추가하고 **기존 8787 규칙보다 위로** 올린다(순서는 위에서부터 첫 일치 — 로컬 관리 문서 기준, 원격 관리 UI 도 같다고 «추정»).
10. Access 에서 해당 호스트 앱이 **Path 비움(호스트 전체)** 인지 확인. 경로별 앱이면 `/rt` 에도 같은 정책의 앱을 추가.
11. 휴대폰 앱용: Access 에 서비스 토큰을 만들고 `/rt` 앱에 **Service Auth** 정책 추가(앱 시기에).
12. 시험: 브라우저 개발자도구에서 `/rt` 가 `101` 로 열리는지, Access 만료 후 어떻게 되는지.

### 되돌리는 방법
- Cloudflare 의 `/rt` 규칙 삭제(또는 Access 에서 막기) → app.js 의 rtStream 은 5초 간격 재시도 후 포기·SSE 가 계속 담당. 코드 변경이 남아도 무해.
- rtcore 는 정지해도 옛 대시보드에 영향 없음(별 프로세스).

## 6. rtcore 쪽 판단 (3번 항목)
- **평문 웹소켓을 터널 뒤에 두어도 되는가**: 읽기 전용 시세·체결 요약 정도면 «Access 가 앞에서 막는다» 전제로 허용 가능. 한계: ①터널·Access 설정이 틀리면 인증 없이 열린다(저장소에서 검증 불가) ②Origin 검사 없으면 CSWSH 로 로그인된 사용자의 브라우저가 대신 읽을 수 있다 ③서비스 토큰 엄격 모드·정책 변경에 종속. 그래서 위 단계 2·3 은 필수. 구독 자료에 **계좌·포지션·주문 상태**가 들어가는 순간(설계 §5 의 계좌·포지션 반영) 최소한 앱 수준 토큰(예: Access 가 붙여 주는 `Cf-Access-Jwt-Assertion` 헤더의 서명 검증)을 rtcore 에서 직접 확인해야 한다. 다만 헤더 이름·검증 방법은 이번에 문서를 확인하지 않았다(미확인).
- **한 문 vs 따로**: 읽기 전용 구독(`/rt`)과 주문 채널은 **따로** 둔다. 이유: 주문은 쓰기·승인(§8)·2단 확인이 걸리고 장애 격리·접근 정책(서비스 토큰 범위)을 따로 줘야 함. 주문은 웹소켓보다 일반 HTTPS 요청(멱등 키)이 단순.
- **휴대폰 앱**: 같은 `/rt` 를 서비스 토큰 헤더로 쓸 수 있다고 «추정»(핸드셰이크가 HTTP GET 이므로). 웹소켓 + 서비스 토큰 조합은 문서에 명시가 없어 **시험 필요**.

## 7. 확인 못 한 것 (사용자에게 묻는 질문)
1. 터널의 게시된 애플리케이션 목록: 호스트가 몇 개이고, 모두 `127.0.0.1:8787` 인가? Path 칸을 쓰는 규칙이 이미 있는가? 원격 관리 UI 에서 경로별로 다른 포트를 지정할 수 있는가(문서는 암시만)?
2. Access 앱이 호스트 전체인가, 경로별인가? 정책은 이메일 허용인가 IdP 인가? 세션 길이는(웹소켓 도중 만료되면 어떻게 되는지)?
3. 호스트가 둘(루트·하위)이면 둘 다 Access 뒤인가? 하나가 빠져 있으면 `/rt` 가 그쪽으로 열린다.
4. 서비스 토큰이 이미 있는가(안드로이드 설계 문서가 저장소에 없음 — 요청에 따라 «설계돼 있다»는 말만 확인)?
5. 시작 스크립트의 `--url` 이 원격 관리 터널에서 무시되는지(실제 ingress 는 대시보드가 이긴다고 «추정»).
6. Cloudflare 웹소켓 유휴 종료 시간(문서에 수치 없음) — 서버 ping 간격을 이 값으로 정해야 한다. 실제 시험으로 측정.
7. 개발기에서는 터널·서버에 접속하지 못해(규율) 위 모든 «됨/안 됨»은 서버에서 직접 시험하기 전까지 **문서 기준**이다.

## 8. 갱신 (2026-11-21 · 지금 코드 기준)

**이미 된 것**: 위 5절 «코드가 할 일» 1~4 는 rtcore `hub.rs` 에 들어갔다 — 경로 `RTCORE_PATH`(기본 `/rt`, 그 밖 404) · Origin 허용 목록 `RTCORE_ALLOW_ORIGINS`
(쉼표 · **글자 그대로 비교** · Origin 머리 없는 비브라우저 도구는 받음 · **목록이 비면 브라우저는 하나도 못 붙음**) · 동시 연결 `RTCORE_MAX_CONNS`(기본 16) ·
연결당 구독 `RTCORE_MAX_SUBS`(기본 8) · 20초 ping(`RTCORE_PING_SECS`). app.js 는 `ensureRtStream()`(그림자 구독 · 6번의 «SSE·폴링을 쉰다»는 아직 안 함 —
재기만 해서 60초마다 `/api/client-timing` 에 `rt_*` 칸으로 보낸다: 지연 중앙·상위 1%, SSE 와 같은 초 값 일치·어긋남 수, 먼저 받은 쪽, 실패·재연결 수).
규칙이 없는 지금은 `/rt` 가 옛 서버로 가서 404(또는 Access 302) → 앱은 5초에서 두 배씩 60초까지 쉬며 다시 묻는다(콘솔에 브라우저가 찍는 실패 한 줄이 1분에 한 번꼴).

**사용자가 Cloudflare·서버에서 할 일(화면이 준비됐을 때)**
1. 터널 → 게시된 애플리케이션: `<호스트>` + Path `^/rt$` → `http://127.0.0.1:8788` 을 **기존 8787 규칙보다 위에**(위 9번과 같다).
2. Access 앱이 호스트 전체인지 확인(위 10번). 경로별이면 `/rt` 에도 같은 정책.
3. 서버의 rtcore 환경에 **`RTCORE_ALLOW_ORIGINS=https://<브라우저 주소창의 호스트>`** — 브라우저가 싣는 Origin 그대로(포트 443 은 안 붙는다 · 끝 `/` 없음 · 대소문자 그대로).
   주소가 둘(예: 루트와 하위 호스트)이면 둘 다 쉼표로. 비워 두면 브라우저 연결은 전부 403 이다(그림자 대조기·앱은 Origin 이 없어 계속 붙는다).
   바꾼 뒤 rtcore 를 다시 띄워야 읽는다(감시자 아래면 rtcore 에 SIGTERM → 15초 뒤 재기동).
4. 확인: 대시보드를 연 채 서버 로그 `client_timing … rt_lat_n=…` 줄이 60초마다 찍히면 붙은 것 · `rt_fail_n` 만 늘면 404/403(규칙·Origin 확인).
   브라우저 개발자도구 네트워크 탭에서 `/rt` 가 `101` 이면 규칙이 맞다.
5. 되돌리기: Cloudflare `/rt` 규칙 삭제 — 화면은 원래 SSE 로 그대로 돈다(그림자라 보이는 것이 바뀐 적이 없다).
