## 2. 보유시간 — 과거 데이터 프런티어 (`research_hold_horizon_frontier_history_20260913.py`)

사용자 지시(*"원장을 토대로 진행하지 말고 과거 데이터를 가지고 진행해. 원장은 정답이 아니야"*)로
원장 68건 반사실(§2-보조)은 **진단으로만 남기고**, 플랜은 869일 5분봉(2021-12~2026-09)의
스케일 없는 계수로 바꿨다. 방향 정확도 a 는 원장 값이 아니라 **파라미터**다.

| H | k_b = E\|r\|/atr | k_s = SD/atr | 변동성 5분위 k_b 범위 | TRAIN→TEST |
|---|---|---|---|---|
| 60분 | 3.52 | 5.49 | 3.26~3.83 | 3.50→3.58 |
| 240분 | 7.37 | 11.29 | 6.56~8.45 | 7.32→7.51 |
| 1440분 | 20.69 | 30.60 | 15.75~27.08 | 20.53→21.15 |

계수가 분위·연도에서 안정(±15%)하므로 «지금 atr_pct × k» 가 현재 상황의 표가 된다.
b_H = k_b·atr, σ_H = k_s·atr, L(H) 는 라이브 MAE 모델. g(H,a) = L((2a−1)b_H − 5.88) − ½(Lσ_H)².

**지금(atr_pct 3.87bp/봉 = 최하 분위, 전체 중앙 11.8)의 프런티어:**

| H | \|r\| bp | 손익분기 a* | g@55% | g@62% |
|---|---|---|---|---|
| 60분 | 13.6 | **71.6%** | −.0038 | −.0022 |
| 240분 | 28.5 | 60.3% | −.0030 | +.0002 |
| 480분 | 42.1 | 57.0% | −.0026 | +.0021 |
| 1440분 | 80.2 | 53.7% | −.0028 | +.0062 |

읽는 법: 잔잔한 장에서 **1시간 보유는 비용을 못 넘는다**(필요 정확도 72%). 정확도가 오를수록 최적
지평이 길어진다(비용 상각이 분산 페널티를 이긴다): 52%→2h · 55%→8h · 57% 이상→1일.
변동성이 3배가 되면 같은 정확도에서 짧은 지평도 비용을 넘는다(자체점검에 고정).
⚠️(2a−1)·E|r| 은 정확도가 움직임 크기와 독립일 때만 맞다(09-12 15분 되돌림에서 8배 과대 전례).
표는 H 사이의 **순위**용이다. 기준 정확도 55% 는 고정값(`ACC_DEFAULT`, `ponytail:`).

### 2-보조. 원장 68건 고정-H 반사실 (진단 전용, 플랜에 쓰지 않음)
고정 60분 11.35bp(t=2.29, 일군집 CI 0 제외) · 1일 −3.55 · 실제 청산 21.25bp(t=3.70, 중앙 67분).
원장이 말하는 «엣지는 1시간 안» 과 과거 데이터가 말하는 «잔잔한 장의 1시간은 비용 벽» 은
모순이 아니다 -- 전자는 사용자 재량 진입의 조건부 정확도가 매우 높다는 주장이고, 후자는 그
주장을 믿지 않을 때의 기준선이다. n=68·20일이라 전자를 플랜의 근거로 쓰지 않는다.

## 3. 분할 — 무엇이 근거 있고 무엇이 없나

- 시간 분할 진입: 09-13 `research_entry_tranche_count` 대로 4시간 이하 보유에서는 일괄이 낫다.
  게다가 진입 경로의 `recommended_tranches` 는 입력 배수가 항상 모델 상한 이하라(cap ≤ cap_model ⇒
  청산거리 ≥ 안전MAE) **항상 1 을 돌려준다**. 버그가 아니라 구조이고, 의미 있는 곳은 **청산 경로**
  (이미 과대한 포지션)뿐이다. 화면의 «일괄» 표시는 그래서 정보가 없다.
- 물타기(역행 중 추가): 09-06 크기 매칭 후 **24/24 전패** → 금지.
- 피라미딩(순행 중 추가): TRAIN/VAL 6/6 CI>0, OOS CI 0 포함 → **허용하되 근거 약함**으로 표기.
- 가격 목표 부분익절: 09-06 컨테이너 비교 0이김/108짐, 청산 축 종결(09-11) → 만들지 않음.
- **위험 예산 분할 청산**: 같은 부등식 N ≤ E·L(R) 을 R 마다 풀면 «R분 더 들려면 몇 % 닫아야
  하나»의 사다리가 나온다. 역행으로 E 가 줄면 자동으로 조여진다. 이것이 유일하게 근거 있는 분할 청산이다.

## 4. 배포한 것

`scripts/live_eth_trade_plan_20260913.py` (`plan_now`) — 기존 함수 조립 + ①보유시간 프런티어(과거 계수 × 지금 atr_pct) ②예산 사다리.
`dashboard/server.py` `assemble_entry_plan`/`assemble_exit_plan` 이 `plan["trade_plan"]` 을 붙인다
(1분봉 변동성 조회를 `realized_vol_now` 로 뽑아 진입·청산이 공유). `app.js` `tradePlanLines` 가 카드에
네 줄(권고 보유 · 기대 체결 · 분할 규칙 · 예산 사다리)을 그리고, 보유 select 옆 배지에 «권고 N분».
검사: 모듈 자체점검 24/24 · 진입 계획 71/71 · 미리보기 밀폐 테스트 5/5(`trade_plan` 첨부 + 물타기 거부 + 음성 대조 2종) · app.js 파서 통과.

플랜 출력 예(라이브 09-13 04:25 위험표, 순자산 1,000·롱):
```
hold = {정확도 55% 가정 최적 480분 · 손익분기 60분 72% … 1440분 54% · 정확도별 최적 52%→120 … 66%→1440}
size = {leverage 8.0, safe_mae 1.82%, total_notional 8,000}
execution = {entry peg_gtx 기대체결 1.8초@vol 10, exit peg_repeg 마감 51초}
entry_split = {일괄, add_allowed: 평가손익≥0 && 여유>0}
exit_ladder(명목 5,000) = {budget 480분, 1440분 → 14% 닫기}
```

## 4-보조. 🔴표시와 집행 — 무엇이 실제 제약인가

사용자 지적(*"진입과 청산 로직을 안 바꾼 거야?"*)이 옳았다. 첫 판의 `trade_plan` 은 전부
`build_entry_plan`/`build_exit_plan` **뒤에** 얹은 표시용이라 수량·가격·주문유형을 하나도 안 바꿨다.
규칙이 화면 문자열로만 있으면 규칙이 아니다. 그래서 근거가 확실한 하나를 집행으로 올렸다.

| 항목 | 근거 강도 | 판정 |
|---|---|---|
| **역행 중 추가(물타기) 금지** | 09-06 크기 매칭 **24/24 전패** | ✅ **집행** — submit 이 `avgdown=1` 없이 400 |
| 보유시간 권고 | 과거 계수는 단단하나 정확도 a 는 가정 | ❌ 표시 — 자동 선택하면 «1일 들 생각인데 8시간짜리 크기»가 된다 |
| 예산 사다리 최소 청산 | 모델 하한 | ❌ 표시 — 09-13 설계대로 «하한 제시, 사람이 더 닫는다». 확인 버튼에 이미 나온다 |
| 진입 시간 분할 | 4시간 이하 일괄이 낫고 진입 경로는 구조적으로 항상 1 | ❌ 표시 |

물타기 판정은 **같은 방향만** 본다(헤지 모드에서 반대 다리는 물타기가 아니다).
`blocked` 로 완전히 막지 않는 이유: 미리보기는 보여야 하고, 완전히 막으면 상한 없는 거래소
화면으로 밀려난다. 그래서 «한 번 더 확인»이다 — 확인 버튼에 🔴물타기 가 붙고 그 버튼만 통과시킨다.
음성 대조 2종(override 통과 · 평가이익 중엔 미발동)과 버그 재주입 검증까지 테스트에 넣었다.
