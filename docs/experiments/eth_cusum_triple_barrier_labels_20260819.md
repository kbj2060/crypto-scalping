# ETH CUSUM(정보기반 이벤트) + triple-barrier 라벨 빌드 (2026-08-19)

**상태: 라벨 빌드+스모크테스트 완료, 기본 설정(cusum_k=1.0)에서 이미 DC보다 심한 비용-경제성
경고 발견 — 학습/평가 미실시**

**⚠️ 정정(같은 날, 이후)**: 이 문서 전체(및 cusum_k 스윕 절)가 쓰는 "30bp 미만이면 위험"
기준은 저장소 어디서도 확인하지 않은 임의값이었다. 실제 코드 비용가정
(`train_eval_omega1_2_tabm_diffusion_risk_20260603.py:47-49`: FEE_RATE=5bp/side,
SLIP_RATE=2bp/side, MAKER_FEE_MULT=0.20)으로 재계산한 실제 왕복비용은 6bp(양쪽메이커)
~14bp(양쪽테이커)이며, 이 기준으로는 CUSUM(k=1.0)의 OOS 평균 TP폭(30.2bp)도 최악의
경우 대비 2.2배 여유가 있다(<14bp 비율 12.3% — 아래 57.0%가 아님). 아래 스윕 실험의
방향성(cusum_k를 올려도 vol_at_entry가 안 변해 "개선"이 배리어 자동튜너의 부수효과일
뿐이라는 결론)은 유효하지만, 심각도의 절대 수치는 30bp가 아니라 6~14bp 기준으로 다시
읽어야 한다. 상세: `eth_tabm_label_logic_retest_initiative_20260819` 메모리.

## 배경

`entry_exit_edge_external_labeling_literature_review_20260819.md` Part A에서 선정한 재테스트
후보 3개 중 ②번. Financial Innovation(2025) "Algorithmic crypto trading using
information-driven bars, triple barrier labeling and deep learning"(DOI:10.1186/s40854-025-00866-w)
레시피를 `core/event_label_engine.py`의 `event_method='cusum'`으로 실제 ETH 데이터에 적용했다.

**중요 배경**: 이 정확한 레시피(정보기반 이벤트 샘플링+대칭 배리어+DL)는 2026-08-10
`entry_exit_edge_root_cause_and_literature_review_20260809.md` Part 5(A)에서 이미 독립
구현·테스트돼 AUC 0.49~0.51(동전던지기), falsification_audit 35th percentile로 기각된
바 있다. 사용자는 그 이후 feature set(LOB raw L2)/자산범위(BTC/SOL)/배리어 버그수정 등
환경이 달라졌다는 이유로 재검증을 지시했다(`eth_tabm_label_logic_retest_initiative_20260819`
메모리). 이번 세션은 **라벨 생성 단계만** 다시 만들었다 — 이전 시도의 학습 결과를
재사용하지 않고 독립적으로 재현한다.

후보①(Directional-Change, `docs/experiments/eth_directional_change_labels_20260819.md`)과
동일한 원시 bar, 동일한 배리어 자동튜닝(`calibrate_barriers`)+sparse 출력 설계를 그대로
따라서, 바뀌는 축은 이벤트 샘플링 메커니즘(DC 가격반전 vs CUSUM 누적합)뿐인 통제된 비교가
되게 했다 — 두 후보 모두 barrier-mode/event-density 재확인 없이 후보①에서 승인된 설계를
그대로 이어받았다(사용자가 명시적으로 재확인을 요구하지 않았고, 두 축이 이벤트 샘플링
메커니즘과 독립적이라 그대로 유지하는 게 통제 실험 원칙에 맞음).

## 구현

신규: [scripts/build_eth_cusum_triple_barrier_labels_20260819.py](../../scripts/build_eth_cusum_triple_barrier_labels_20260819.py)

후보①과 거의 동일한 구조 — 차이는 이벤트 검출 부분뿐:
```python
vol = engine.ewma_volatility(full["close"], span=args.vol_span)
threshold = (args.cusum_k * vol).to_numpy()
event_idx = engine.cusum_filter(full["close"].to_numpy(), threshold)
```
`cusum_k`(엔진 기본값 1.0)가 DC의 `dc_theta`에 대응하는 튜닝 레버다. 파일명 계약
(`zigzag_action_labels_{year}.csv`)은 후보①에서 스모크테스트로 발견한 교훈을 처음부터
반영해 시작부터 올바르게 썼다(별도 수정 불필요).

## OOS 구간 비용-경제성 체크 (후보①과 동일 방법론)

후보①에서 TP/SL폭 중앙값의 34.4%가 30bp 미만이라는 우려가 나왔던 것과 같은 방식으로,
CUSUM 기본 설정도 즉시 확인했다:

| | DC(theta=0.004, 채택) | DC(theta=0.002, 기각됨) | **CUSUM(cusum_k=1.0)** |
|---|---:|---:|---:|
| OOS 이벤트 수 | 2,053 | 4,233 | **8,678** |
| 하루 평균 | 23.1건 | 47.6건 | **97.5건** |
| 평균 간격 | 62.4분 | 30.3분 | **14.8분** |
| 평균 보유 | 20.5분 | 21.5분 | 19.4분 |
| TP/SL폭 중앙값 | 0.353% | 0.333% | **0.277%** |
| TP폭 < 30bp 비율 | 34.4% | 40.6% | **57.0%** |

**CUSUM은 기본 설정(cusum_k=1.0)만으로 이미 DC의 "기각된" 고빈도 실험(theta=0.002)보다
더 나쁜 경제성을 보인다** — 이벤트의 절반 이상(57%)이 30bp 미만 TP폭이고, 평균 간격(14.8분)이
평균 보유시간(19.4분)보다 짧아 순수 신호빈도로 보면 포지션이 거의 항상 겹치는 수준이다.
DC 실험에서 확인한 패턴("이벤트 샘플링을 더 촘촘하게 만들수록 경제성이 나빠진다")이 CUSUM
에서도 재현됐고, 폭도 더 심하다.

이건 2026-08-10에 이 정확한 레시피가 AUC 0.49~0.51로 기각된 것과 무관하지 않을 수 있다 —
**라벨의 절반 이상이 비용 문턱 근처의 미세한 가격변동이라면, 모델이 배울 수 있는 "방향
정보"가 애초에 그 절반에서 노이즈에 가까웠을 가능성**이 있다. 이건 가설이며 이번 세션에서
직접 검증하지는 않았다.

## 스코프 경고

이 문서의 라벨 통계만으로는 방향 edge를 주장할 수 없다(`docs/label_methodology_survey_20260815.md`
— 40개 이상의 선행 라벨 방법론이 전부 "학습 가능하나 방향 edge 없음"으로 수렴, 이 정확한
CUSUM+TB+DL 레시피는 2026-08-10에 이미 한 번 학습까지 거쳐 기각됨). 위 비용-경제성 체크도
"라벨이 비쌀 것 같다"는 사전 진단일 뿐, 실제 학습+Fresh-Forward 평가를 대체하지 않는다.

## DC vs CUSUM 유사도 (같은 날, 전체 2024-2026)

`docs/experiments/eth_directional_change_labels_20260819.md`(후보①)와 이벤트 타이밍·방향·분포
3축으로 통계 비교했다. **사실상 포함관계**: DC 이벤트의 75.5%가 CUSUM과 정확히 같은 bar,
94.9%가 5분·99.6%가 15분 이내에 매칭(CUSUM=DC+추가 미세이벤트 4.8배). 매칭 지점의 방향
일치율은 매우 높음(같은 bar 100%, 5분 94.1%, 15분 92.9%) — 두 방법이 모순된 신호를 내는 게
아니다. 일별 이벤트수 상관은 약함(Pearson 0.125) — DC는 고정임계값이라 고변동성 날에 몰리고
CUSUM은 임계값이 EWMA vol에 비례해 매일 고르게 발동하기 때문. `vol_at_entry` KS=0.220(전체
지표 중 최대 격차, CUSUM 평균 0.0018 < DC 0.0024) — CUSUM의 추가분이 체계적으로 더 조용한
구간에서 나온다는 뜻이며, 이게 아래 cusum_k 스윕에서도 재확인된다.

## cusum_k 상향 스윕 (같은 날) — "개선"의 실제 원인 분해

사용자 지시로 `cusum_k ∈ {1.5, 2.0, 3.0, 4.0}`(빈도를 낮추는 방향, DC의 theta 실험과 반대축)를
스윕했다.

| cusum_k | 배리어(pt=sl_mult) | OOS 이벤트 | 하루평균 | TP폭 중앙값 | TP<30bp | vol_at_entry 중앙값 |
|---|---:|---:|---:|---:|---:|---:|
| 1.0(기존) | 1.5 | 8,678 | 97.5건 | 0.28% | 57.0% | 0.00185 |
| 1.5 | 2.0 | 5,770 | 64.8건 | 0.37% | 32.7% | 0.00186 |
| 2.0 | 2.0 | 4,170 | 46.9건 | 0.37% | 31.9% | 0.00187 |
| 3.0 | 2.0 | 2,423 | 27.2건 | 0.38% | 31.1% | 0.00188 |
| 4.0 | 2.0 | 1,591 | 17.9건 | 0.37% | 30.9% | 0.00187 |
| (참고) DC θ=0.004 | 1.5 | 2,053 | 23.1건 | 0.35% | 34.4% | - |

**핵심 발견 — 개선은 대부분 착시.** `vol_at_entry` 중앙값이 0.00185~0.00188로 cusum_k 4배
구간에서도 거의 평평하다 — cusum_k를 올려도 CUSUM은 "더 변동성 큰" 구간을 골라내지 않고,
같은 변동성 분포에서 이벤트 개수만 줄인다. k=1.0→1.5에서 TP<30bp가 57.0%→32.7%로 급격히
좋아진 건 `calibrate_barriers`가 그 지점에서 pt_mult를 1.5→2.0으로 바꿔 골랐기 때문
(1.5→2.0=33% 증가, 실제 TP폭 증가 0.28%→0.37%=32%와 거의 일치) — **CUSUM 자체의 이벤트
선별력이 아니라 배리어 자동튜너의 부수효과.** mult가 2.0으로 고정된 k=1.5~4.0 구간에서는
이벤트가 3.6배 줄어드는 동안 TP<30bp는 32.7%→30.9%로 거의 안 움직인다.

k=2.0~3.0 부근에서 이벤트 수(4,170~2,423건)와 경제성(31~32%)이 DC(2,053건, 34.4%)와 거의
같은 지점으로 수렴하는데, 이는 CUSUM이 그 지점에서 DC와 비슷하게(큰 임계값 = 드문 확정
이벤트) 행동하기 시작한다는 뜻이지 CUSUM 고유의 장점이 아니다.
